1. Introduction

This document specifies the JSON-LD document that MeshNotes produces and consumes as its native annotation format. A MeshNotes export is a single W3C Web Annotation Data Model [WADM] AnnotationCollection that gathers the annotations placed on one 3D model, together with the description of that model, the annotation groups, optional model-level notes, and an optional structured metadata report.

The format is W3C Web Annotation at its core, extended in two controlled ways. First, the geometry of each annotation is identified by a MeshNotes 3D selector, defined in the companion MeshNotes 3D Selector Specification [SEL]; that document is normative for everything inside an annotation's selector, including the coordinate frame, WKT notation, CRS handling and model-binding hash, and is not repeated here. Second, MeshNotes-specific information that the W3C model does not cover is carried under the meshnotes: namespace, resolved through the JSON-LD context at https://meshnotes.org/ns/context-v1.jsonld.

The design goal is interoperability: a consumer that understands only the W3C Web Annotation Data Model can read every annotation, its target, its bodies and its grouping, and ignore the meshnotes: extensions; a consumer that understands the extensions additionally recovers the full editing state for a faithful round-trip. The format is designed to be cleanly mappable to CIDOC CRM and ingestible by infrastructure such as NFDI4Objects, though it emits neither RDF nor LIDO directly in this version.

2. Namespaces and conformance

A document conforms to this specification when:

  • its top-level resource is an AnnotationCollection carrying the members marked must in §3;
  • it declares "dcterms:conformsTo": "https://meshnotes.org/spec/annotation/v1/" at the collection level;
  • every annotation it contains is a W3C Annotation whose target.selector conforms to [SEL];
  • its terms resolve through the JSON-LD context at https://meshnotes.org/ns/context-v1.jsonld;
  • it validates against the JSON Schema at https://meshnotes.org/spec/annotation/v1/schema.json.

A few coordinate-frame and identity terms — upAxis, unit, annotationType, surfaceProjection — are intentionally exposed without the meshnotes: prefix (the context aliases them) so that non-JSON-LD consumers can read them as plain keys; all MeshNotes-implementation-specific members retain the prefix. A consumer should tolerate either the aliased or the fully-qualified meshnotes: form of these terms.

The key words must, must not, should, should not and may are used as defined in RFC 2119.

6.1 creator

creator identifies the author of an entry as a person.

MemberReq.TypeDescription
typeshouldstring"Person".

  "id": "https://orcid.org/0009-0003-7750-2818",
  "type": "Person",
  "name": "Nils Schnorr"
}

Because id maps to @id in the W3C Web Annotation context, the ORCID URI is a first-class node identifier for the author — the conventional, interoperable way to attach an ORCID to a Web Annotation creator, and a clean attachment point for a CIDOC CRM E21 Person mapping.

When an entry is edited by a different person, the body's creator reflects the entry's current author and modified the time of the edit; every prior state, with its own author, is preserved in meshnotes:versions (§6.2), and the annotation-level creator (§5) stays frozen on the annotation's original author. The W3C model is silent on re-edited embedded bodies; this is the documented MeshNotes interpretation. In a CIDOC CRM mapping, the annotation-level creator corresponds to the E21 Person who carried out (P14) the E65 Creation of the annotation; each entry edit is a separate, later event.

6.2 meshnotes:versions

Each element of meshnotes:versions records a superseded state of the entry, oldest to newest, as { "value", "creator" (optional), "schema:url" (optional), "meshnotes:savedAt" }. This preserves the edit history for accountability in collaborative documentation.

7. Groups

Annotations are organised into named, colour-coded groups. Group definitions are carried in meshnotes:groups; each annotation references its group by UUID (meshnotes:groupUuid), and group colours are also expressed as an oa:CssStylesheet so that a generic W3C consumer can render them via each target's styleClass.

MemberReq.TypeDescription
idshouldnumberProducer-internal group id; matches the styleClass suffix and the stylesheet selector. Not a durable identifier.
meshnotes:uuidshouldstringPersistent group UUID; the value referenced by meshnotes:groupUuid on annotations.
schema:nameshouldstringGroup name.
schema:colorshouldstringGroup colour (CSS hex).
meshnotes:visiblemaybooleanGroup visibility state.
meshnotes:opacitymaynumberGroup opacity, 0.0–1.0.

8. Model Information and Metadata

modelInfo carries free-text notes about the model as a whole. It is shaped as a W3C Annotation with "motivation": "describing" and a body array of TextualBody entries identical in structure to §6, but it has no geometric target — it describes the model rather than a region of it.

metadata carries the structured meta- and paradata report (project, capture, reference, processing, paradata and legal information). Its internal field structure is producer-defined and is treated as an open object by this version of the format; a consumer may preserve it verbatim on round-trip and should not reject unknown members within it. A future version may give this block a normative schema and a CIDOC CRM / LIDO crosswalk.

9. Coordinate frame, units and model binding

All geometric coordinates in this format — within selectors and their embedded points — follow the coordinate frame, WKT notation, CRS rules, rotation convention and model-binding hash defined normatively in [SEL] §3 and §5. In summary: coordinates are Z-up and right-handed in the model's local frame; the up-axis and unit are declared on modelSource (§4); face identifiers in surface selectors are a non-authoritative hint valid only against the mesh identified by modelSource.schema:sha256.

10. Extensibility and unknown terms

The format is deliberately open. A conforming consumer must ignore members it does not recognise rather than reject the document, and should preserve them on round-trip where feasible. Within version 1, MeshNotes may add further optional members (in the meshnotes: namespace, or as context-aliased plain keys) without a version bump; it will not add new required members, remove members, or change the meaning of an existing member within version 1. The accompanying JSON Schema (§12) is correspondingly lenient: it validates the required core and the shape of known members, and permits additional properties.

10.1 Survey alignments and surveyed positions (added 2026-10-04)

This subsection was added on 2026-10-04 under the rule of §10. It describes the optional members that MeshNotes 1.6 and later write for survey points imported from a CSV file and placed on the model by a control-point alignment, together with three optional state flags (annotation lock, group label visibility, group collapse) and the model's centring offset. Every member is optional and is omitted when there is nothing to record. None of them is required, none changes the meaning of an existing member, and the selector ([SEL]) is untouched: each annotation's position on the model is still given only by its target.selector. A consumer that does not know these members ignores them (§10) and still places every annotation correctly.

Where the members appear

MemberReq.TypeDescription
meshnotes:alignmentsmayarrayOn the collection (§3), after meshnotes:groups: the survey alignments of the model, each a meshnotes:SurveyAlignment node (below).
meshnotes:defaultAlignmentmayIRIOn the collection: the id of one of the listed alignments, preselected by the producer for new imports.
meshnotes:frameOriginmaystringOn modelSource (§4): the offset by which the producer centred the loaded model, as WKT POINT Z (x y z) in the exported Z-up frame. An exported coordinate plus frameOrigin gives the position in the model's coordinates as loaded (after any node transforms of the file and the up-axis conversion, expressed Z-up). It is a shift only: when the model file contains node rotations or scales, it does not by itself lead back to the file's raw vertex coordinates. Informative; MeshNotes does not read it on import.
meshnotes:labelsVisiblemaybooleanOn a group (§7): false when the name labels of the group's annotations are hidden in the 3D view. Written only as false; absence means labels shown.
meshnotes:collapsedmaybooleanOn a group (§7): true when the group's list is collapsed in the producer's sidebar. Written only as true; absence means expanded.
meshnotes:lockedmaybooleanOn an annotation (§5), next to annotationType, for any annotation type: true when the annotation's position is locked against editing in the producer. Written only as true; absence means unlocked. It does not affect the geometry.
meshnotes:surveyedPositionmayobjectOn a point annotation (§5), next to annotationType: the surveyed coordinate of a point imported from a survey file, a meshnotes:SurveyedPosition node (below).

Frame convention

An alignment maps a point p = [x, y, z] in the exported coordinate frame — the Z-up frame whose numbers are written as meshnotes:wkt ([SEL] §3), i.e. the model's local frame — to survey coordinates [E, N, H] (Easting, Northing, Height): 

survey = R · p + t

R is the rotation given by the unit quaternion meshnotes:rotation in the order [x, y, z, w], the same component order as the box selector's meshnotes:rotation in [SEL]; it rotates the model axes into the survey axes. t is meshnotes:translation, [E, N, H]. The inverse is p = Rᵀ · (survey − t); a consumer should perform the subtraction first, in double precision, because survey coordinates are large (e.g. seven-digit UTM northings). The fit is rigid: there is no scale, so the alignment assumes that the model is at true scale in the survey's units. Survey coordinates are metric and projected; they are named Easting, Northing and Height rather than written as geo:asWKT, because a GeoSPARQL literal must follow its coordinate system's own axis order. Residuals are [dE, dN, dH] = surveyed minus fitted position, in the survey's units (metres).

The alignment does not georeference the model in the sense of [SEL] §3.3. Its meshnotes:crsLabel is a free-text label entered by the user (e.g. "EPSG:32635"); it is not an IRI, is not validated, and is not modelSource's meshnotes:crs (§4). It never governs the georeferenced selector form, and selectors stay in the model's local frame.

SurveyedPosition

A point annotation imported from a survey file keeps its surveyed coordinate beside its geometry. Its selector holds its position on the model: the surface point nearest to its fitted position (Rᵀ · (survey − t) of its alignment), the fitted position itself when the producer could not query the surface (meshnotes:surfaceDistance is then absent), or the position it was moved to by hand. The fitted position is not stored separately; it can be recomputed from the surveyed coordinate and the alignment.

Terms and context

New terms in the meshnotes: namespace (§11): SurveyAlignment, SurveyedPosition, alignments, defaultAlignment, frameOrigin, crsLabel, heightColumn, modelSha256, modelUpAxis, fitType, translation, quality, controlPointCount, rms, rmsHorizontal, rmsVertical, maxResidual, scaleDiagnostic, tiltDeg, headingDeg, controlPoints, enabled, modelPosition, residual, looError, alignmentVersions, surveyedPosition, alignment, easting, northing, height, rawValues, attributes, placement, surfaceDistance, row, locked, labelsVisible, collapsed. The existing term meshnotes:rotation is reused with the meaning of [SEL]; id, type, created, modified, creator, schema:name, schema:sha256 and dcterms:source are existing vocabulary.

The JSON-LD context gained additive term definitions only; no existing definition changed: meshnotes:translation and meshnotes:residual are ordered lists ("@container": "@list", as meshnotes:rotation already was), meshnotes:alignment and meshnotes:defaultAlignment are node references ("@type": "@id"), and meshnotes:rawValues and meshnotes:attributes are JSON literals ("@type": "@json", which requires JSON-LD 1.1 processing). The other new terms need no definition: they expand through the meshnotes: prefix. The JSON Schema (§12) is unchanged; it already permits these members.

Compatibility

  • A consumer that ignores these members reads every annotation, including imported survey points, at its correct position, because the selectors are unchanged.
  • MeshNotes versions before 1.6 load such files with all annotations in place. They ignore the alignments, surveyed positions, locks, group flags and frame origin, and drop them when the file is exported again.
  • Files without these members are read by MeshNotes 1.6 as before.
  • When MeshNotes merges two files (informative), alignments are matched by id; the copy with the later modified wins, the other fit is kept in meshnotes:alignmentVersions, and survey points with meshnotes:placement "fit" follow the winning alignment.

11. Versioning policy

The term namespace https://meshnotes.org/ns/ is unversioned and append-only: identifiers, once published, keep their meaning permanently, and new terms are only ever added. This specification, its JSON Schema, the companion JSON-LD context and the selector specification are versioned and frozen: a breaking change is published at a new version path and the prior version remains resolvable indefinitely, so that files referencing it continue to validate.

12. Conformance and validation

A document can be validated structurally against the JSON Schema at https://meshnotes.org/spec/annotation/v1/schema.json (JSON Schema draft 2020-12). The schema is forward-compatible: it checks the required members of the collection, the model description, annotations, targets, selectors and bodies, applies light pattern checks to WKT and identifier strings, and otherwise permits additional properties. Semantic rules that JSON Schema cannot express — polygon ring closure, quaternion normalisation, the hint status of face identifiers — are stated normatively in [SEL] and are not enforced by the schema.
